# Safety and Privacy

This document covers five things per `SPEC.md` Phase 8: the synthetic-data
boundary, why no PHI would reach an external inference endpoint in a
production design, audit logging of model calls, human-in-the-loop
confirmation before anything enters a chart, and the deliberate choice not
to generate billing codes. Each section states what's actually implemented
today versus what a production deployment would need, rather than
presenting the demo-scope version as if it were already the production one.

## The synthetic-data boundary

Every patient, condition, medication, encounter, observation, and clinical
note this project touches is generated by [Synthea](https://github.com/synthetichealth/synthea),
MITRE's open-source synthetic patient generator. `data/synthea_output/` is
gitignored and regenerated locally by `python -m previsit.ingest.synthea_runner` -
nothing in it is, or is derived from, a real person's medical record. No
component of this project connects to a real EHR, a real HL7/FHIR
endpoint, or any data source that could contain real PHI. This boundary is
absolute for the project as built: there is no code path, configuration
flag, or environment variable that points any part of this system at real
patient data.

## Why no PHI would reach an external inference endpoint (production design)

As built, this project's LLM calls (Gemini, Groq) send patient-derived
text to those providers' APIs - which is fine here specifically *because*
the data is synthetic, but would not be fine with real PHI without
additional controls a production deployment would need to add:

- **Provider choice matters.** `previsit.llm.azure_openai` already exists
  as a swappable provider (`LLM_PROVIDER=azure` in `.env`) specifically
  because Azure OpenAI Service is offered as part of Microsoft's
  HIPAA-eligible service set under a Business Associate Agreement (BAA),
  with contractual guarantees that submitted data is not used to train
  models and can be configured for regional data residency. Gemini and
  Groq's free tiers, used in this project's demo and eval work, carry no
  such guarantee and would not be appropriate for real PHI.
- **De-identification before the LLM sees anything, not just provider
  choice.** A production design should not rely on provider BAAs alone -
  the deterministic layer (`sql/gaps/*.sql`, `previsit.agent.tools`)
  already computes every clinical decision (is a screening overdue, is a
  value uncontrolled) before the LLM is invoked, so the LLM's job is
  narration of already-decided findings, not open-ended access to a raw
  chart. That narrows what needs to reach the model to specific,
  citation-backed facts rather than an entire record - a smaller, more
  auditable surface than "send the whole chart and ask a question."
- **Network isolation.** A production deployment would run inside a VNet
  with Azure OpenAI accessed via a private endpoint, not the public
  internet - not implemented in this local-Docker demo, which has no VNet
  to isolate.

## Audit logging of model calls

**Current state (development-grade, not production audit logging):** the
citation guardrail (`previsit.agent.guardrails`) logs every rejected
finding and every severity coercion via Python's standard `logging`
module - which finding, which reason, which category (hallucination vs.
schema violation vs. coercion) - see `guardrails.py`'s `logger.warning`/
`logger.info` calls. This is real, inspectable logging, but it goes
wherever the process's logging is configured to go (stdout by default),
not to a structured, persisted, tamper-evident store. Separately,
`eval/run_eval.py` logs every eval run's parameters and metrics to MLflow
(`mlruns.db`) - but that covers *evaluation* runs, not live interactive
usage of the agent (FastAPI, Streamlit, MCP server), which currently has
no persisted call log at all.

**What a production audit trail would need**, none of which is built
here: every model call persisted with the exact prompt sent, the raw
response received, the model/version used, a timestamp, which findings
were accepted vs. rejected vs. coerced and why, and which user (clinician
or system) triggered the request - written to an append-only or
tamper-evident store, not application logs that can be rotated away.
Given the deterministic-first architecture, most of what needs auditing is
already structured (`source_resource_ids` on every finding), which would
make a real audit log considerably simpler to build than for a system
where the LLM has open-ended access to source data - but "simpler to
build" is not "already built."

## Human-in-the-loop confirmation before anything enters a chart

This project has **no write path to any chart at all** - every tool
(`previsit.agent.tools`) is read-only, and the `PreVisitCard` the agent
produces is a summary artifact for a clinician to read, never written back
into `dim_patient`, `fact_condition`, or any other table. There is
consequently no human-in-the-loop confirmation step to describe for this
version, because there is nothing downstream of the card that a
confirmation step would gate.

If a future version added a write-back feature (e.g. "accept this
documentation-gap finding and it gets added as a note to the chart"), the
design principle this project would hold that feature to is: **no agent
output enters the official record without an explicit clinician action
confirming it first**, findings would need to remain reversible/attributable
to that clinician's decision rather than the model's, and the same
citation guardrail that gates what appears on the card today would need to
gate what's eligible to ever be confirmed in the first place. This is a
stated design principle for work that doesn't exist yet, not a tested
feature - listed here so it isn't silently assumed if this project is ever
extended.

## The deliberate choice not to generate billing or diagnosis codes

`SYSTEM_PROMPT` (`previsit.agent.prompts`) explicitly states the agent "is
NOT a diagnostic tool, and you do NOT suggest, recommend, or imply any
billing or diagnosis code," and `find_documentation_gaps`'s output framing
is hard-coded to a single template - `"[symptom] documented in [N]
notes/visits, no corresponding condition is on the coded problem list -
please review"` - never "add code X" or "this is likely condition Y."
This is enforced at the prompt level and verified directly in
`tests/test_agent_tools.py` (`test_recurring_symptom_diabetic_uncoded_triggers_gap`
asserts the word "add" never appears in a documentation-gap's detail
text). The reasoning: a documentation gap is evidence for a human to
review, and turning it into a coding suggestion would put the agent in the
position of practicing medicine (or billing) rather than surfacing
information a clinician can act on - exactly the line `SPEC.md`'s "Things
to explicitly NOT do" draws.
