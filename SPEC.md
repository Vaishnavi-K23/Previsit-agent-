# Build Spec: Pre-Visit Clinical Intelligence Agent

> Paste this whole file into Claude Code / Cursor as the opening instruction.
> Then work **one phase at a time**. Do not let the agent skip ahead.

---

## 0. Context for the coding agent

You are helping me build a portfolio project that demonstrates AI/ML engineering skill in a healthcare setting.

**The problem being solved:** A walk-in primary care clinic sees patients who booked nothing in advance. Before the provider enters the room, a staff member has roughly one minute to scan the patient's chart and surface what matters — overdue screenings, uncontrolled chronic conditions, and symptoms mentioned in old notes that never made it onto the coded problem list. This project automates that one minute.

**The output** is a "pre-visit card": a structured summary a provider reads in ~15 seconds, where every single claim is traceable to a specific source record.

**Critical framing:** This is a *documentation completeness and care-gap detection* tool. It is explicitly **not** a diagnostic tool and **not** a billing-code optimizer. Every design decision should reinforce that.

---

## 1. Non-negotiable rules

These are hard constraints. Do not violate them even if a simpler path exists.

1. **Synthetic data only.** Every patient record is generated by Synthea. No real patient data, ever. No connections to real EHR systems. State this prominently in the README.
2. **Zero paid services.** No API key that requires a credit card on file. No Azure subscription. No OpenAI paid tier. If a step seems to require payment, stop and ask me — there is always a free path.
3. **Every claim must cite a source.** If the system asserts "mammogram overdue," it must carry the identifier of the record proving it. If it cannot cite, it must not assert. Enforce this in code, not just in the prompt.
4. **Deterministic logic stays deterministic.** Care-gap detection is date math and code lookups. It goes in SQL. The LLM never decides whether a screening is due.
5. **No HEDIS claims.** NCQA's HEDIS specifications are licensed material. We implement *guideline-inspired approximations* based on publicly available sources (USPSTF, ADA Standards of Care, CDC schedules). Label them as such everywhere. Never claim HEDIS compliance or certification.
6. **Measure everything.** Any feature that produces output must have a corresponding test in the eval harness before it is considered done.
7. **The LLM provider is swappable.** All model calls go through one abstraction layer. Switching to Azure OpenAI must be a config change, never a code change.

## 2. Tech stack

Chosen to mirror a real Azure-based healthcare AI stack while costing nothing.

| Layer | Tool | Why this one | Cost |

| LLM inference | **Google AI Studio (Gemini)** free tier OR **Groq** free tier | Both give real API keys with no credit card | Free |
| Agent framework | **LangGraph** | Named in the job description | Free |
| API layer | **FastAPI** + `uvicorn` | Named in the job description | Free |
| MCP server | `mcp` Python SDK (FastMCP) | Named in the job description. Very few candidates build one. | Free |
| Demo UI | **Streamlit** | Fastest path to a shareable demo | Free |
| Experiment tracking | **MLflow** (local file backend) | Named in the job description. Tracks eval runs. | Free |
| Data generator | **Synthea** (MITRE) | Industry standard synthetic FHIR generator | Free |
| Testing | `pytest` | Standard | Free |

| CI | GitHub Actions | Named in the job description (as Azure DevOps — note the equivalence in README) | Free |

## 4. Phased build

**Work through these in order. Do not start a phase until the previous one's acceptance criteria pass.**

### Phase 0 — Environment

- `docker-compose.yml` bringing up SQL Server 2022 and Qdrant
- `pyproject.toml` with dependencies pinned
- `.env.example` documenting every variable
- Health-check script confirming both containers reachable from Python

**Acceptance:** `docker compose up -d && python -m previsit.healthcheck` prints green for both services.

---

### Phase 1 — Data generation and inspection

- Script to download and run Synthea, generating **1,000 patients in Arizona** with FHIR R4 output
- An exploration notebook or script that prints: every distinct resource type present, counts per type, and a sample of each

**Important instruction:** Do **not** hardcode clinical codes from memory or from this document. Synthea's code sets vary by version. Inspect the actual generated JSON and build the code sets empirically from what is really there. Write the discovered codes into `docs/DATA_MODEL.md` with counts.

**Acceptance:** 1,000 bundles on disk. A written inventory of resource types and the actual LOINC/SNOMED codes present, with frequencies.

---

### Phase 2 — Relational layer

Parse these FHIR resource types and load into SQL Server:

| FHIR resource | Table | Key fields |
|---|---|---|
| `Patient` | `dim_patient` | patient_id, birth_date, gender, deceased_flag, city, state, postal_code |
| `Condition` | `fact_condition` | condition_id, patient_id, code_system, code, display, onset_date, abatement_date, clinical_status, verification_status |
| `Observation` | `fact_observation` | observation_id, patient_id, encounter_id, code, display, value_numeric, value_string, unit, effective_datetime |
| `MedicationRequest` | `fact_medication` | medication_id, patient_id, code, display, status, authored_on |
| `Encounter` | `fact_encounter` | encounter_id, patient_id, class, type_code, type_display, start_datetime, end_datetime |
| `Procedure` | `fact_procedure` | procedure_id, patient_id, code, display, performed_datetime |
| `DiagnosticReport` | `fact_diagnostic_report` | report_id, patient_id, code, display, effective_datetime, conclusion_text |
| `Immunization` | `fact_immunization` | immunization_id, patient_id, code, display, occurrence_datetime |

Requirements:
- Every table keeps a `source_resource_id` column holding the original FHIR resource id. **This is what citations point to.** Non-nullable.
- Every table keeps `ingested_at`.
- Idempotent loads — re-running must not duplicate rows.
- Indexes on `patient_id` and on `(patient_id, code)` for observation, condition, procedure.
- Bulk insert, not row-by-row. 1,000 patients is a lot of rows.

**Acceptance:** Row counts reported per table. A query for one patient returns a coherent history. Loading twice produces identical row counts.

---

### Phase 3 — Care gap engine, **no LLM**

This is the deterministic core. Implement each rule as a `.sql` file returning a consistent shape:

```
patient_id, gap_code, gap_title, severity, detail, source_resource_ids (comma-separated), rule_version
```

Implement these eight rules. Each must cite its public guideline source in `docs/CARE_GAP_RULES.md`:

1. **A1c not tested** — patient has active diabetes; no HbA1c observation in last 12 months
2. **A1c uncontrolled** — most recent HbA1c ≥ 8.0%
3. **Diabetic eye exam overdue** — active diabetes; no retinal/ophthalmic exam procedure in last 12 months
4. **Blood pressure uncontrolled** — active hypertension; most recent systolic ≥ 140 or diastolic ≥ 90
5. **Breast cancer screening overdue** — female, age 40–74, no mammogram procedure in last 27 months
6. **Colorectal screening overdue** — age 45–75, no colonoscopy in 10 years and no stool-based test in 12 months
7. **Statin gap** — diabetes, age 40–75, no active statin medication
8. **Influenza vaccination overdue** — no influenza immunization in the current season

Rules must exclude deceased patients and respect `clinical_status` / `abatement_date` so resolved conditions don't trigger gaps.

Wrap in `gaps/engine.py` returning typed `Gap` pydantic objects.

**Acceptance:** `python -m previsit.gaps.engine --patient <id>` prints gaps with source ids. Population-level counts look clinically plausible (spot-check five patients manually against their raw FHIR). Unit tests cover boundary conditions — exactly 12 months, exactly age 40, resolved conditions.

> **Stop here and show me results before continuing.** If this phase feels wrong, the rest is built on sand.

---

### Phase 4 — Note retrieval

- Extract narrative text from Synthea output (`DocumentReference` resources and `DiagnosticReport.conclusion`; check what your generation actually produced)
- Chunk with overlap, preserving `patient_id` and `source_resource_id` in metadata
- Embed locally with `all-MiniLM-L6-v2`
- Store in Qdrant with a payload filter on `patient_id`

**Critical:** every vector search must be hard-filtered by `patient_id` at the database level. Cross-patient leakage is the single worst bug this system could have. Write an explicit test for it.

**Acceptance:** semantic search for "numbness tingling extremities" on a diabetic patient returns relevant chunks with correct source ids. Test proves patient A's query never returns patient B's text.

### Phase 5 — Agent layer

LangGraph agent with exactly these tools:

```python
get_patient_summary(patient_id) -> PatientSummary
    # SQL. Demographics, active conditions, active meds, latest vitals.

check_care_gaps(patient_id) -> list[Gap]
    # Calls Phase 3 engine. Deterministic. LLM does not reason about due dates.

search_notes(patient_id, query, k=5) -> list[NoteChunk]
    # Vector search, patient-filtered.

find_documentation_gaps(patient_id) -> list[DocumentationGap]
    # Hybrid: pull candidate condition mentions from notes, check against
    # coded problem list, return what appears in narrative but is not coded.
    # Output framing must be "appears in notes, not on problem list — please
    # review", never "add this code".

get_recent_encounters(patient_id, months=12) -> list[Encounter]
    # SQL. Especially flags ED visits without follow-up.
```

The graph should: gather structured data first, then decide whether narrative search is warranted, then compose the card.

**Output model — enforce with pydantic:**

```python
class Finding(BaseModel):
    category: Literal["care_gap", "uncontrolled_condition",
                      "documentation_gap", "recent_event"]
    statement: str
    severity: Literal["high", "medium", "low"]
    source_resource_ids: list[str]  # min_length=1, enforced

class PreVisitCard(BaseModel):
    patient_id: str
    one_line_summary: str
    findings: list[Finding]
    generated_at: datetime
    model_used: str
```

**Guardrails in `guardrails.py`:**
- Reject any `Finding` with an empty `source_resource_ids`
- Verify every cited id actually exists in the database
- Verify the cited record is for the correct patient
- On failure: drop the finding, log it, and count it as a hallucination in eval — never silently pass it through

**Acceptance:** running against a patient produces a valid `PreVisitCard`. Deliberately prompt-inject a request for an uncited claim and confirm the guardrail drops it.

### Phase 6 — Eval harness

**This is the phase that makes the project credible. Do not cut it.**

`eval/ground_truth.py` computes truth **directly from the raw Synthea FHIR bundles**, using a completely independent code path from the SQL engine. If both were written the same way, you'd only be testing that a bug is consistent.

Metrics to compute over ≥100 held-out patients:

| Metric | Definition |
|---|---|
| Gap recall | true gaps found / true gaps existing |
| Gap precision | correct gaps reported / gaps reported |
| Hallucination rate | findings with invalid or missing citations / total findings |
| Citation validity | cited records that actually support the claim / total citations |
| Patient leakage | any finding citing another patient's record — **must be 0** |
| Latency p50/p95 | seconds per card |

Log every run to MLflow with the model name, prompt version, and rule version as parameters.

Write results into `docs/EVAL_RESULTS.md` as a table, including failure examples. **Show the failures.** A project that reports 100% on everything reads as untested.

**Acceptance:** `python -m eval.run_eval --n 100` produces a metrics table and an MLflow run. Leakage is zero.

## 5. Things to explicitly NOT do

- Do not let the LLM compute dates or decide whether a screening is due
- Do not use vector search for questions that have exact answers in SQL
- Do not generate or suggest billing/diagnosis codes as recommendations
- Do not build a patient-facing chatbot
- Do not add a feature without adding its eval
- Do not use real clinical data from any source
- Do not claim HEDIS or NCQA compliance
- Do not commit `.env`, model weights, or Synthea output
